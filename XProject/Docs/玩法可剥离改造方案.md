# XProject 通用模块梳理与玩法可剥离改造方案

## 1. 改造目标与原则

### 1.1 目标
将当前工程改造为“**通用壳层（框架 + 系统）**”与“**玩法插件（TripleMerge / Dinosaur / 后续玩法）**”解耦形态：
- 通用层只负责启动、加载、状态流转、子系统生命周期、资源与存档基础能力。
- 玩法层通过统一接口接入，不直接反向依赖具体玩法类型。
- 新玩法可独立增删，不需要修改主干启动代码与核心状态机实现。

### 1.2 原则
- **单向依赖**：`Gameplay -> Framework/Common`，禁止 `Framework/Common -> Gameplay具体实现`。
- **组合优先**：玩法通过注册机制挂接，不在 `MyGame` 中硬编码 `AddSubSystem<TripleMergeSystem>()`。
- **可灰度迁移**：先兼容旧链路，再逐步替换，保证 InitScene 主流程可持续运行。

---

## 2. 当前通用模块梳理（按“可沉淀/需解耦”划分）

## 2.1 启动与主循环（可沉淀到通用层）
- `Framework/Main/Main`：Unity 生命周期入口，负责 `Game.Init/Start/Update/LateUpdate/Release` 驱动。
- `Framework/Main/Game`：持有 `SubSystemManager + Fsm`，统一推进系统更新与状态更新。
- `Framework/SubSystems/SubSystemManager`：分组注册、生命周期回调（Init/Start/Update/LateUpdate/Pause/Release）。
- `Framework/Fsm/*`：状态机通用能力（状态注册、切换、异步 PreEnter、EnterFinish）。

**结论**：以上可直接定义为“壳层核心”，后续仅增加抽象，不绑定玩法语义。

## 2.2 通用系统（大体可复用）
- Framework 组：`CoroutineManager`、`RecycleSystem`、`RenderTextureFactory`、`UIViewSystem`。
- Gameplay 组中的可通用能力：`TimeTickModel`、`AudioSysManager`、`GameSettingSubSystem`、`GamePauseManager`、`SaveFileSystem`、`CurrencyModel`。

**结论**：可拆成“CoreServices（与玩法无关）”与“GameplayServices（玩法共享）”两类服务目录。

## 2.3 玩法实现（应完全插件化）
- 三合玩法主入口：`TripleMergeSystem`、`TripleMergeGameplay`、`ITripleMergeComponent`。
- 三合玩法状态：`StateTripleMerge`。
- 三合玩法数据：`MapDataLoader`、`TripleMergeConfigManager`。

**结论**：三合玩法结构内部已有“组件式雏形”，但对外接入仍是硬编码、状态与系统命名耦合。

## 2.4 当前关键耦合点（必须改造）
1. `Game.IsTripleMerge()` 直接判断 `StateTripleMerge` 类型。
2. `MyGame.initSubSystems()` 硬编码注册 TripleMerge 相关系统。
3. `MyGame.initFsm()` 直接注册 `StateTripleMerge`。
4. `Launching` 完成后直接跳转 `FsmStateType.TripleMerge`。
5. `FsmStateType` 枚举包含玩法具体名（`TripleMerge`）。
6. `StateTripleMerge` 中直接处理 Lobby UI 打开逻辑，状态职责偏重。

## 3. 目标架构（壳层 + 玩法插件）

## 3.1 分层模型

### A. Core（通用壳层）
- `BootFlow`：启动流程编排（加载 UI、基础配置、版本检查、入口玩法选择）。
- `AppStateMachine`：仅管理通用状态，如 `Boot / Loading / Gameplay / Pause / Shutdown`。
- `SystemHost`：子系统容器，提供按模块注册。
- `ServiceRegistry`：全局服务查找（替代玩法直连静态单例的扩散）。

### B. Gameplay Runtime（玩法运行时）
- `IGameplayModule`：玩法模块统一接口。
- `IGameplayStateAdapter`：玩法状态适配器，接入 AppStateMachine。
- `IGameplayInstaller`：玩法系统安装器（注册自身 SubSystem、配置、UI、数据加载器）。

### C. Concrete Gameplay（具体玩法包）
- `TripleMergeModule`（现有 TripleMerge 重构而来）。
- `DinosaurModule`（后续新增，按同接口落地）。

## 3.2 核心接口建议
```csharp
public interface IGameplayModule
{
    string Id { get; }                // "triple_merge" / "dinosaur"
    int Priority { get; }             // 多玩法场景下用于入口排序
    void Install(IGameplayInstaller installer);
    IGameplaySession CreateSession(IGameplayContext context);
}

public interface IGameplaySession
{
    UniTask<bool> EnterAsync(object param = null);
    void Update(float deltaTime);
    void LateUpdate(float deltaTime);
    void Exit();
}
```

## 3.3 状态机改造方向
- `FsmStateType` 从玩法命名改为通用命名：`Launch -> Loading -> Gameplay`。
- `Gameplay` 状态内部不感知 TripleMerge，仅委托给 `GameplayDirector.CurrentSession`。
- 玩法切换由 `GameplayCatalog + GameplayDirector` 决定，而非状态机枚举写死。

## 4. 具体改造清单（按优先级）

## P0：先解耦入口与状态（不动玩法内部逻辑）
1. 新增 `GameplayCatalog`（玩法注册表），支持配置默认玩法 ID。
2. 新增 `GameplayDirector`（运行时持有当前 `IGameplaySession`）。
3. 把 `Launching` 完成后的跳转改为通用 `Gameplay` 状态。
4. 新建 `StateGameplay`，把 `StateTripleMerge` 的“进入玩法”行为迁移到 Director。
5. `Game.IsTripleMerge()` 替换为通用查询：`Game.IsInGameplay(string gameplayId)`。

**交付结果**：主流程不再依赖 `StateTripleMerge` 类型判断。

## P1：把 TripleMerge 封装成模块
1. 新增 `TripleMergeModule : IGameplayModule`。
2. 把 `TripleMergeSystem + MapDataLoader + TripleMergeConfigManager` 接入 `Install()`。
3. 把 `TripleMergeSystem.OnEnterTripleMerge/Exit` 封装到 `TripleMergeSession.Enter/Exit`。
4. `StateGameplay.Update` 调度 `CurrentSession.Update`，替代直接调具体玩法系统。

**交付结果**：TripleMerge 可作为单独玩法包接入/移除。

## P2：通用服务分层与边界收敛
1. 将 `MyGame.initSubSystems()` 按 `CoreServices/SharedGameplayServices/GameplayModuleServices` 三段拆分。
2. `SaveFileSystem` 扩展“玩法存档分区”（按 gameplayId 命名空间）。
3. `CurrencyModel` 抽象为可选“全局货币域 + 玩法私有货币域”。
4. UI 入口（如 Lobby）从状态类迁移至 `UIFlowService`，降低状态层 UI 负担。

**交付结果**：系统职责更清晰，后续扩玩法改动面收敛。

## P3：配置与资源装配插件化
1. 为玩法定义 `GameplayManifest`（配置路径、首包资源、预加载列表）。
2. Launch 阶段读取 Manifest，决定资源预热与进度描述。
3. 支持“关闭某玩法包”后仍能成功启动并进入默认玩法。

**交付结果**：玩法包可独立发版与按需装配。

## 5. 建议目录重构（目标形态）

```text
Assets/GameMain/Scripts
├── Core
│   ├── Boot
│   ├── StateMachine
│   ├── Systems
│   └── Services
├── GameplayRuntime
│   ├── Abstractions      // IGameplayModule / IGameplaySession
│   ├── Catalog
│   └── Director
├── Modules
│   ├── TripleMerge
│   └── Dinosaur
└── Shared
    ├── Save
    ├── Config
    └── UI
```

> 说明：这是“目标目录”，不要求一次性迁移，建议通过中间层（适配器 + partial class）分阶段收拢。

## 6. 里程碑与工期建议（可并行）

- **M1（2~3 天）**：P0 完成，主干进入通用 Gameplay 状态，TripleMerge 通过适配器运行。
- **M2（3~5 天）**：P1 完成，TripleMerge 模块化，移除对 `StateTripleMerge` 直连。
- **M3（3~4 天）**：P2 完成，系统分层与 UI/存档边界收敛。
- **M4（2~3 天）**：P3 完成，Manifest 与资源预热插件化。

总计：约 10~15 个工作日，按 1 主程 + 1 功能程可并行压缩。

## 7. 风险与回滚策略

## 7.1 主要风险
- 启动链路被改动后，InitScene 到 Gameplay 可能出现黑屏或状态卡死。
- 玩法模块注册顺序变化可能导致依赖缺失（如配置先后、UIRoot 时序）。
- 存档分区切换不当可能造成旧存档读取失败。

## 7.2 回滚策略
- 保留 `LegacyTripleMergePath` 开关（Script Define Symbol 或配置开关）。
- 每个里程碑保留可运行 tag：`refactor-m1`, `refactor-m2`...
- 存档改造增加版本号迁移器，失败时回退旧解析路径并上报日志。

---

## 8. 验收清单（Definition of Done）

1. 新增或删除某个玩法模块，不需要改 `Main/Game/Fsm` 核心代码。
2. `Launching` 结束后进入通用 Gameplay 状态，由 Director 决定具体玩法。
3. 至少支持 `TripleMergeModule` 正常运行（进入、更新、退出）。
4. InitScene -> Gameplay 全链路通过；暂停/恢复、退出重进正常。
5. 存档与配置加载在模块化后保持兼容（旧号可读）。

---

## 9. 本次落地建议（下一步可直接开干）

### 迭代 1（最小可行改造）
- 先新增抽象层：`IGameplayModule/IGameplaySession`、`GameplayCatalog`、`GameplayDirector`。
- 增加 `StateGameplay`，让 `StateLaunch` 结束进入该状态。
- 写 `TripleMergeModuleAdapter` 包装现有 `TripleMergeSystem`，不改内部组件。

### 迭代 2
- 清理 `MyGame` 里的 TripleMerge 硬编码注册。
- 拆出 `CoreServicesInstaller` 与 `GameplayInstaller`。

### 迭代 3
- 处理 UIFlow 与存档命名空间，完成可复制模板，给 Dinosaur 模块直接套用。

> 按这个顺序推进，你可以在不重写三合玩法内部的前提下，先把“壳层去玩法化”完成，再逐步沉淀真正的多玩法架构。
