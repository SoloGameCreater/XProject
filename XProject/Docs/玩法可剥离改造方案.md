# XProject 通用模块梳理与玩法可剥离改造方案（校准版）

## 1. 改造目标

将当前工程改造为“通用壳层 + 玩法模块”的解耦形态，满足以下目标：

1. 启动链路不直接依赖具体玩法状态名（如 `TripleMerge`）。
2. 玩法通过统一模块接口接入，支持新增/下线玩法时最小改动主干代码。
3. 玩法存档注册从硬编码改为模块声明，降低后续扩展成本。
4. 保持 InitScene 主流程可运行，并保留过渡兼容能力。

---

## 2. 现状核验与科学性评估

## 2.1 已核验的关键耦合点

以下耦合点在当前仓库真实存在：

1. `Main/Launching.cs`：加载完成后直接 `ChangeState(FsmStateType.TripleMerge)`。
2. `Main/MyGame.cs`：`initSubSystems` 硬编码注册 `TripleMergeSystem`、`TripleMergeConfigManager`、`MapDataLoader`。
3. `Main/MyGame.cs`：`initFsm` 硬编码注册 `StateTripleMerge`。
4. `Framework/Main/Game.cs`：`IsTripleMerge()` 直接依赖 `StateTripleMerge` 类型。
5. `Framework/Fsm/IFsmState.cs`：`FsmStateType` 含玩法特定枚举项。
6. `TripleMerge/FSM/StateTripleMerge.cs`：承担玩法进入 + Lobby UI 打开，状态职责偏重。

## 2.2 原方案遗漏点（已补充）

1. `Framework/Fsm/FSM.cs` 内仍存在 `MainGame <-> TripleMerge` 特判分支（遗留硬编码）。
2. `Common/SubSystems/SaveFileSystem.cs` 直接注册 `SaveFileTripleMerge`，不满足玩法可剥离。
3. `SubSystemManager` 是 `new T + Init + GlobalSystem.Instance` 模式，不适合“运行时动态新增子系统”，更适合“启动期安装 + 运行时切会话”。

## 2.3 科学性结论

原方向正确，但需要从“纯接口设计”调整为“与当前框架约束一致的增量改造”路径：

1. **先去状态硬编码**，再推进玩法模块化。
2. **先做运行时会话切换**，不在首阶段做子系统热插拔。
3. **先保持旧 API 兼容**（如 `IsTripleMerge`），逐里程碑下线。

---

## 3. 校准后的目标架构

## 3.1 分层

1. `Core`：启动、FSM、子系统宿主、通用服务。
2. `GameplayRuntime`：
   - `IGameplayModule`
   - `IGameplaySession`
   - `GameplayCatalog`
   - `GameplayDirector`
3. `Modules`：具体玩法实现（当前先接 `TripleMergeModule`）。

## 3.2 接口约束（与现有代码一致）

首阶段接口异步采用 `Task`，保持与 `IFsmState.PreEnterAsync` 一致，避免首轮引入 `Task/UniTask` 混用改造。

---

## 4. 已实施改造（2026-02-10）

## 4.1 状态机与启动链路

1. `FsmStateType` 新增 `Gameplay`。
2. 新增 `StateGameplay`，作为通用玩法状态。
3. `Launching` 完成后跳转改为 `FsmStateType.Gameplay`。
4. `FSM` 移除 `MainGame <-> TripleMerge` 的特判硬编码分支。

## 4.2 GameplayRuntime 抽象落地

新增：

1. `IGameplayContext`
2. `IGameplayInstaller`
3. `IGameplayModule`
4. `IGameplaySession`
5. `GameplayIds`
6. `GameplayCatalog`
7. `GameplayDirector`
8. `GameplayInstaller`
9. `GameplayBootstrap`

## 4.3 TripleMerge 模块适配

新增：

1. `Modules/TripleMerge/TripleMergeModule.cs`
2. `Modules/TripleMerge/TripleMergeSession.cs`

行为：

1. 三合相关子系统由 `TripleMergeModule.Install()` 注册。
2. 进入/退出玩法由 `TripleMergeSession` 承接。
3. 原 `StateTripleMerge` 保留，作为过渡兼容状态。

## 4.4 MyGame 与通用查询能力

1. `MyGame.OnInit`：统一注册内建玩法模块并初始化 `GameplayDirector`。
2. `MyGame.initSubSystems`：移除三合硬编码注册，改为 `GameplayCatalog.InstallModules`。
3. `Game` 新增 `IsInGameplay(string gameplayId)`。
4. `Game.IsTripleMerge()` 改为优先走通用查询，保留兼容回退。

## 4.5 存档注册解耦（第一步）

1. `SaveFileSystem` 不再硬编码 `SaveFileTripleMerge`。
2. 改为通过 `GameplayCatalog.CollectSaveFiles` 收集玩法存档。
3. 增加按类型去重，避免重复注册冲突。

## 5. 后续里程碑（未完成）

## M2：兼容收敛

1. 逐步替换外部直接 `ChangeState(FsmStateType.TripleMerge)` 调用（如后续新增点）。

## M4：资源与装配

1. 加入 `GameplayManifest`（预热资源、配置路径、入口描述）。
2. 启动阶段按 Manifest 决定预热与进度提示。

## 6. 验收指标（量化）

## 6.1 功能正确性

1. `InitScene -> Launch -> Gameplay` 到达率 100%。
2. `TripleMergeModule` 可正常进入、退出、重进。
3. 暂停/恢复流程中，`GameplaySession` 不重复初始化。

## 6.2 兼容性

1. 老存档可读取（读取失败时有明确日志并可回退）。
2. 旧调用 `Game.IsTripleMerge()` 行为与改造前一致。

## 6.3 稳定性

1. 改造后不新增 `ChangeState new state is null` 级别错误。
2. 关键加载链路无黑屏卡死（以 QA 回归清单覆盖）。

---

## 7. 回滚策略

1. 保留 `StateTripleMerge` 与 `Game.IsTripleMerge()` 兼容路径。
2. 若通用 Gameplay 链路异常，可临时将 `Launching` 跳转回 `FsmStateType.TripleMerge`。
3. 每个里程碑打可回退 tag，确保问题可快速回滚。
